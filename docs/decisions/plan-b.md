# Plan B — decisions (what · why · cost if wrong)

- The API client exposes `apiRequest(method, path, schema, body?)` and `apiRequestNoContent` instead of the spec's single `request()` sketch · a schema is required whenever a body is expected, so every response is parsed (D27) · none
- `signOut()` clears the token first, then the caches · the route guards leave signed-in screens before their queries lose data · none
- Notices published outside React (401 → "session ended", deletion) are shown by `<NoticeToaster />` · HeroUI's `useToast()` only works inside the provider · none
- React Navigation's theme is built from HeroUI tokens (`useNavigationTheme`) · headers, the tab bar and screen backgrounds follow light/dark without literals · none
- Tabs import from `expo-router/js-tabs` · the root `Tabs` export is deprecated in Expo Router 57 · none
- The splash uses `expo-splash-screen` directly · expo-router's `SplashScreen` export is marked hidden · none
- The root `ErrorBoundary` uses plain RN + Uniwind classes, not HeroUI · it must render even when the providers are what failed · it looks slightly plainer
- Session hydration uses `useSyncExternalStore` · the React Compiler lint rejects setState inside an effect · none
- A 401 signs out only while the token it carried is still the current one · concurrent requests with an expired token, or a late answer after deleting the account, would otherwise stack "session ended" toasts or sign out the next user · none
- The splash waits only for the first GET /me; a retry keeps the error screen up with "Try again" disabled · after the splash hides, rendering null showed a blank window for the whole retry · none
- Form fields never read `field.ref`; the email → password focus hand-off uses a `useRef` passed as `ref` · the React Compiler lint (`react-hooks/refs`) flags reading the controller's field object · react-hook-form can't focus the first invalid field by itself
- Form layouts use `KeyboardAwareScrollView` (`bottomOffset={144}`) from react-native-keyboard-controller (D20) · the focused field stays visible on every screen size, and the offset also covers the helper line, gap and 56 pt submit button (≈ 102 pt, measured from the caret, which sits ≈ 16 pt above the field's bottom) plus a 24 pt margin, so the button stays visible under the focused last field, even with the form Alert shown · none
- Icon glyph sizes are numeric props, but icon colours always come from className tokens (`withUniwind(Ionicons)`) · Ionicons only accepts a numeric `size`, like HeroUI's own `iconProps` · none
- `FormScreen` calls the scroll view's `assureFocusedInputVisible()` from the fields container's `onLayout` · react-native-keyboard-controller re-scrolls only on keyboard, selection, text and input-height events, so a form Alert or inline error that pushed the focused field down left the submit button under the keyboard (`onContentSizeChange` never fires while the `grow` content is shorter than the screen) · an extra no-op re-check on every fields re-layout
- The onboarding CTA scrolls with the form instead of sticking above the safe area · the resting form fits an iPhone 16 viewport with "Start training" clear of the home indicator, and each helper line adds only ≈ 26 pt, which the scroll view absorbs · on a smaller phone, or with all three helper lines showing, the button needs a short scroll
- The open card's accent border fades in as an overlay (opacity 0 → 1) instead of interpolating colours · colours stay className tokens · none
- `greeting()`: 05–11 morning, 12–17 afternoon, otherwise evening · "Good morning" at 1 a.m. read wrong in the smoke run · none
- The Plan screen's `RefreshControl` gets `progressViewOffset={insets.top}` · the scroll view runs under the status bar (the safe area is content padding, so the header can scroll beneath it), which put the 60 pt refresh control behind the Dynamic Island and the spinner was never visible · none on a notch-less device, where the offset only moves the spinner down by the status bar height
- The Plan's `RefreshControl` is bound to a local `isPulling` flag, not `plan.isRefetching` · the refetch on mount after a cache restore and every foreground refetch would otherwise show the spinner and push the content down · a failed pull hides the spinner without a message, but the cached plan stays on screen
- The unlock motion and the plan-complete card wait `REVEAL_DELAY_MS` (350 ms) before they play · `useIsFocused` flips as the pop transition starts, so the 350–450 ms fades would run under the outgoing session screen; the start values are seeded in a layout effect so no frame paints the end state · the restart path, which has no transition, starts a third of a second late
- The plan-complete card animates with shared values driven by `animate`, not `entering` · `entering` runs only at mount, and the card mounts under the session screen when the last completion writes the cache, so it would never play · none
- The session screen leaves through `backToPlan()`: `router.back()` when `router.canGoBack()`, otherwise `router.replace('/')` · a cold deep link (a stale or mistyped `session/…` link) opens the route with nothing beneath it, so the brief's plain `router.back()` did nothing ("GO_BACK was not handled") and, with no header back button either, "Back to plan" and the post-completion pop left the user stranded; the celebration still plays because the Plan mounts focused with the pending celebration · a root-layout `unstable_settings.anchor = '(tabs)'` would give every cold deep link (profile too) a real back stack, but it touches the guarded root stack, so it is left for the walkthrough
- The paywall's Android status-bar padding is chosen at runtime (`Platform.OS === 'android' && 'pt-safe'`), not with `android:pt-safe` · `android:` variants were observed to apply on iOS with Uniwind 1.12.0 in Expo Go (a plain `android:pt-10` leaked the same way; the cause is not established), which pushed the sheet's content down by the 59 pt top inset and ran the cards into the footer · none; any other `ios:`/`android:` class in the app needs the same treatment
- The paywall's error Alert renders in the footer, above "Start 7-day trial", instead of at the end of the scroll content · at the end of the content it sat under the footer on an iPhone 16 and needed a scroll to read · while the Alert shows, the taller footer clips the bottom of the selected card (the content still scrolls)
- The "No purchases to restore on this account." toast covers the paywall's CloseButton for its 4 s · HeroUI's top placement is shared by every toast in the app, the toast can be swiped away and the sheet still dismisses with a swipe down · the close control is unreachable for 4 s after a restore that found nothing
- Coach bubbles use FadeIn, not the spec's FadeInDown, and user bubbles don't animate at all · the list is inverted, so a vertical entering animation would run upside down; and the optimistic user bubble is swapped for the server's copy (new id, so a new cell) when the reply lands, which replayed the fade on a bubble already on screen · a slightly flatter entrance, and the user's own bubble simply appears
- The chat uses keyboard-controller's `KeyboardAvoidingView behavior="padding"` · it measures its own frame, so the tab bar needs no offsets · none
- A coach send that times out (15 s) is rolled back and never retried, although the server may still complete the queued POST (observed with a frozen API: "Hello" and its reply were in the history after the thaw) · the contract has no idempotency key, so a client retry could only duplicate the message, and the next history fetch (foreground refetch) shows the server's copy · a user who taps Send again after a timeout can end up with the same message twice
- Settings keeps the brief's spacing and scrolls on an iPhone 16: at rest the list overflows by ≈ 139 pt (bottom padding included), so "Delete account & data" and the version line need a scroll · fitting them above the tab bar would cost ≈ 55 pt (tighter section gaps plus a smaller avatar) and flatten the hierarchy for the sake of one destructive row, and a settings list that scrolls is what iOS Settings does · the destructive row and the version sit out of sight until the user scrolls
- The Settings membership row branches on `entitlement.data` first: a skeleton row while the query is pending or a retry is in flight, a tap-to-retry row ("Couldn't load membership") once it has failed, and the Free / Plus rows only from real data · `['entitlement']` is neither persisted nor placeholdered, so a Plus user launching offline would otherwise see "Free — See Forge Plus" and be sent to the paywall · offline, the row stays a skeleton for ≈ 48 s (three 15 s timeouts plus backoff) before the retry row appears
